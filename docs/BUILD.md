# Building and Deploying the NativeCoop Module

## Source Location

**One source of truth:** `wse2work/Native-Coop-master/`

This is the ONLY module system directory. There is no other copy. All edits go here.

## Prerequisites

- Python 2.7 at `C:\Python27\python.exe` (the classic Warband module system does not run on Python 3)
- Visual Studio with the MSVC x86 toolset (C layer)
- Mount & Blade: Warband 1.174 installed (Steam), with the WSE2 rev-1145 binaries in the game directory. WSE2 is **pinned at revision 1145** (v1.1.4.5, Mar 2026): every hook address and binary patch is keyed to those exact binaries, so a different WSE2 build will not work. Release zips ship them pre-patched; from source, apply the four client exe patches in `docs/wse2-binary-patches.md`
- A `Modules\NativeCoop\` directory in the game install
- `wse2work/Native-Coop-master/module_info.py` — set `export_dir` to your game's `Modules/NativeCoop/` path (this is where the build writes its output)

## Module Build (Full)

Always run a full build. Partial builds cause "Invalid Quick String ID" errors at runtime.

```cmd
cd wse2work\Native-Coop-master
.\build_module.bat
```

`build_module.bat` runs `run_module_build.py`, which executes the 29
`process_*.py` steps in order and stops at the first step that exits
non-zero or prints an `ERROR` line or a traceback (several legacy steps
print `ERROR` and still exit 0). The bat's exit code is 1 on failure, 0 on
success, so it is safe to chain.

The build also regenerates the tracked `ID_*.py` tables in the source
directory (written in binary mode so they keep LF endings; a build after
an unchanged source leaves them untouched). Commit them together with
the module change that altered them.

One-liner that works around the environment quirks below (from any shell, via cmd):

```cmd
cmd /c "cd /d <repo>\wse2work\Native-Coop-master && set PATH=C:\Python27;%PATH% && .\build_module.bat"
```

Environment quirks:

- **Bare `build_module.bat` may fail with "not recognized"** even from the
  correct directory — hardened Windows setups exclude the current
  directory from cmd's executable search
  (`NoDefaultCurrentDirectoryInExe`). Invoke it as `.\build_module.bat`.
- **`python` on PATH must be Python 2.7** — with Python 3 first, every
  step dies with `SyntaxError: Missing parentheses in call to 'print'`.
  Prepend `C:\Python27` to PATH for the invocation (as above).

### Module Deploy

The build writes the compiled `.txt` files directly to `export_dir` (your game's `Modules/NativeCoop/` folder). No manual copy needed.

**Exception:** Resource files (`.brf`), `module.ini`, `Data/`, `SceneObj/`, `Music/`, `Sounds/`, `Textures/`, `Resource/` are NOT generated by the build. These are the module's static assets. If they are missing after a fresh install, copy them from `wse2work/Native-Coop-master/output/`.

## Deploy Configs and Launch Scripts

After building the module, copy the server configs and launch scripts into the game directory:

```bash
cp deploy/configs/*.txt             "<game>/Configs/"
cp deploy/configs/server_config.ini "<game>/"
cp deploy/scripts/*.bat             "<game>/"
cp deploy/coop.ini                  "<game>/"
```

`deploy/configs/` contains one `BattleServer_<n>.txt` per battle slot (0–3) plus `CampaignCoop.txt` for the campaign server.

## Launching

From the game directory, either start everything at once:

- `coop_launch_all.bat [N]` — campaign server + N battle-server slots (default 2, max 4) + a client
- `coop_launch_all_debug.bat [N]` — the same, with every party map-visible on the campaign server (no fog of war). It sets `COOP_DEBUG_REVEAL=1` for the campaign server; the host plugin writes it into `WSE\NativeCoop\coop server cfg campaign.wsedict` and the module's reveal trigger reads it. The normal launcher leaves it off.

or start each process individually:

1. **Campaign server:** `coop_campaign_server.bat` (WSE2 dedicated campaign, port 7240)
2. **Battle servers:** `coop_battle_server_<n>.bat` for each slot n = 0–3 (slot n listens on port 7241 + 2n; the pool auto-adapts to however many slots are running)
3. **Client:** WSE2 launcher → select NativeCoop module → Multiplayer → join the campaign server

## Building the Client ASI (warband_coop.asi)

The client ASI injects the campaign server into the MP browser (Direct Connect from `coop.ini`), hooks native screen-close events, and writes the battle-server address into string register s59, and mirrors the join password into s57 for module_simple_triggers.py's deferred battle connect. It is loaded by the dinput8 ASI loader on the **client** (`mb_warband_wse2.exe`) only.

### Source Files

```
src/asi/
  coop.c                  # Browser hook, server injection, s59 writer
  steam_flat.c/h           # Steam API flat-vtable shim (MSVC callback layout)
  steam_tunnel.c/h         # Steam P2P tunnel thread (host bridge / joiner proxy / invites)
src/shared/
  hook.c/h                # Engine memory hooks
  modglobals.c/h          # Module-global (variables.txt) name resolution
  warband_addrs_wse2.c/h  # Engine address tables (client + dedicated)
```

### Build

```cmd
build\build.bat
```

(from bash: `cmd.exe //c build\\build.bat`)

The script auto-detects Visual Studio via `vswhere.exe`, sets up the x86 environment, and produces `bin\warband_coop.asi`.

## Building the Host Plugin (CoopWSEPlugin.dll)

The host plugin runs inside both dedicated-server binaries: in **COOP_HOST** mode (campaign server) it reads/writes module globals and hosts the ENet IPC listener; in **COOP_BATTLE** mode (battle server) it watches for battle end and signals the campaign server over IPC. The mode is detected from the exe name — no configuration needed.

### Prerequisites

- Visual Studio with the C++ desktop workload (any recent version — `vswhere.exe` auto-detects)
- x86 target (`vcvarsall.bat x86`), not x64 — Warband is a 32-bit game

### Source Files

```
src/
  plugin_main.cpp         # DllMain, plugin entry point, mode detection
  coop_campaign.c/h       # Campaign/battle server logic, IPC handlers, poll thread
  battle_ipc.h            # IPC packet framing (PKT_BATTLE_HELLO / PKT_BATTLE_END)
  wse_plugin.h            # WSE2 plugin API header
src/shared/
  battle_net.c/h          # ENet IPC link (battle server <-> campaign server, port 7242)
  wsedict.c/h             # .wsedict dict-file reader/writer
  modglobals.c/h          # Module-global name resolution + raw memory access
  hook.c/h                # Engine memory hooks
  crash_report.c/h        # Crash reporting + ring buffer
  warband_addrs_wse2.c/h  # Engine address tables (DED_*/CAMP_* for dedicated binaries)
  nettune.c/h              # Runtime net-tuning patcher ([NetTuning] AIMD/packet/send-rate knobs)
  xp.c/h                   # XP accounting helpers
enet/                     # ENet library source (vendored)
```

### Build

```cmd
build\build_plugin.bat
```

Produces `bin\CoopWSEPlugin.dll`.

## Building the Loader Proxy (winmm.dll)

Dedicated servers cannot use the dinput8 ASI loader, so the plugin is loaded by a `winmm.dll` proxy: it forwards all winmm exports to the real system DLL (saved as `winmm_sys.dll`) and loads `CoopWSEPlugin.dll` into processes whose exe name contains `dedicated`. Game clients ship the same proxy on disk but never load the plugin.

```cmd
build\build_loader.bat
```

Produces `bin\winmm.dll`.

## Deploy (C Artifacts)

Automatic — every successful C build ends with a call to `build\deploy.bat`, which:

- auto-detects the Warband install (Steam registry, every Steam library, common drive roots; set `GAMEDIR` to override)
- copies everything present in `bin\` (`warband_coop.asi`, `CoopWSEPlugin.dll`, `winmm.dll`) into the game directory
- creates `winmm_sys.dll` from the system winmm if missing
- installs `coop.ini` from `deploy/coop.ini` if it doesn't already exist

Run `build\deploy.bat` standalone to deploy without rebuilding. If the game or a server is running, the locked file is skipped with a WARN — close them and rerun.

`build\deploy.bat` also deploys `lua\main.lua` to `Modules/COOP/lua/` if present. It does not
package: `build\package_mod.bat` is the manual release step (see CLAUDE.md "Public Export"),
run on purpose by the maintainer. It writes `dist\warband_coop_<timestamp>.zip` by default
(`dist\` is gitignored); set `COOP_PKG_DIR` to write elsewhere, and the script exits with an
error before staging when that destination does not exist.

## coop.ini

The plugin and client ASI read `coop.ini` from the game directory at startup (template: `deploy/coop.ini`):

```ini
[Coop]
Port=7240
HostIP=127.0.0.1
BattlePort=7241
Module=NativeCoop
Password=              ; pool-wide join password, max 47 chars; empty = open

[NetTuning]            ; read by the dedicated exes at startup
AimdFloor=16000        ; congestion-control floor (stock 3000)
AimdStep=8000          ; recovery step (stock 1000)
PacketMaxSize=1200     ; stock 1350 — 1200 fits Steam's measured budget
SendRateHz=30          ; 30 (stock) or 62
BacklogPeriodMs=33     ; send-period ceiling while a player has a backlog (stock 100 = 10 Hz)

[Steam]                ; read by the client ASI only
; SteamHost=1          ; on the HOST machine — publishes the "Join Game" button
; AllowedSteamIDs=     ; host: comma-separated allowlist; EMPTY ACCEPTS ANYONE
; HostSteamID64=       ; on a JOINER machine — 17 digits; ignored if invited
; Debug=1              ; verbose GameNetworkingSockets logging
```

There is no mode key — server role comes from the exe name. On each **client** machine, set `HostIP` to the campaign server's IP: battle joins build their address from it (the ASI writes it into string register s59), and the `127.0.0.1` default silently bounces battle joins back to the MP menu. Steam-tunnel joiners are the exception: an accepted invite or a configured `HostSteamID64` re-aims every coop address at loopback.

Two templates exist: `deploy/coop.ini` is the source-build template that `build\deploy.bat` installs into the game directory if missing, and `deploy/coop_client.ini` is packaged into release zips as `coop.ini.example` (renamed to `coop.ini` on first install so extract-over-install never clobbers a configured one).

`AllowedSteamIDs` is the tunnel's only access control, and an **empty value accepts any SteamID** — if you leave it empty, set a `Password=`.

## Common Errors

| Error | Cause | Fix |
|-------|-------|-----|
| Invalid Quick String ID | Partial module build | Run the full build |
| Module directory is invalid | Space in module name | Use `NativeCoop`, not `Native Coop` |
| UNABLE TO MAP GAME SCRIPT CODE | WSE2 scripts missing in module | Normal for vanilla-compatible scripts |
| Illegal Identifier: itm_cross_end | Missing Battle Time reference | Already fixed — stub definitions are in the module source |
| Invalid Scene_prop ID: -1 | Missing Battle Time scene prop | Already fixed — stub definitions are in the module source |

## Architecture

Three processes cooperate:

```
CLIENT (mb_warband_wse2.exe + warband_coop.asi)
  |  MP browser join (port 7240)   |  B-key battle chooser (port 7241 + 2*slot)
  v                                 v
CAMPAIGN SERVER (dedicated campaign + CoopWSEPlugin.dll via winmm proxy)
  |  ENet IPC (port 7242, persistent per-slot connection)
  v
BATTLE SERVER POOL (up to 4x dedicated + CoopWSEPlugin.dll via winmm proxy)
  slot s (0-3): port 7241+2s, identity from COOP_BATTLE_SLOT env var
```

1. **Campaign server** runs WSE2 dedicated campaign mode: parties, encounters, diplomacy, time. All persistent player state lives in per-player `.wsedict` dict files — the server is authoritative; clients receive pushes and send back deltas over the campaign event channels.
2. When players encounter an enemy, the campaign server allocates a free battle slot, writes battle data (scene, factions, troop stacks) to that slot's dict file, and signals the slot's battle server over ENet IPC. All clients are told which port the battle is on.
3. **Battle server** loads the battle; the initiator auto-connects, everyone else can press B and pick the battle from the chooser. Players spawn with their campaign stats and equipment and fight one life.
4. Battle end writes casualties back to the dict; when participants rejoin the campaign map, the server applies losses, wounds, and XP shares and frees the slot.
5. Small fights and sieges can instead run **locally** on the client as singleplayer missions, reporting the outcome through the same result pipeline.

`docs/flows/` holds one dossier per core flow (battle pipeline, siege, XP sync, inventory sync, party-screen sync, Steam tunnel, campaign server tick).

